# 消融设计（Ablation Design Notes）

**状态**：`v0` — 2026-10-18。主张 2 定稿；主张 1、3 为未定稿骨架（只列已定项与待定项）。
**为什么先写设计**：三条消融的执行成本各约 6–9 h GPU + 一轮 agent 额度，**只够跑一条**；而设计一天能写完。而且设计可能直接判掉一条——功效不足意味着"测不出来"，那和"跑得不够"是两件事。

## 0. 通用约定

- **术语**：本文件用「条件 / 组」，不用「臂」——`docs/backend-selection.md` 里「双臂」已指 bimanual，属于同词不同义。
- **单位**：一次「agent 尝试」= 一个有界求解会话（固定模型、固定轮数上限、固定 tick 预算），产出**冻结的程序**；程序在 held-out 上只跑一次。技能库只被写程序的 agent 读取，程序本身不读库——所以任何"同程序跑两个库"的设计恒等，不是两个条件。
- **held-out 纪律的正解**：禁止的是**用 held-out 反馈迭代**，不禁止为**预注册的多个条件**各跑一次 held-out。两者不冲突的前提是：每个条件的程序在跑 held-out 之前冻结（记录 hash），分析脚本预先写好。
- **锁定项**（跨条件必须完全一致）：模型与版本、每会话轮数/token 上限、每版本 dev sweep 的种子数、tick 预算、harness 版本、worker prompt 模板（除技能库那一段）、种子分区。
- **不锁定就不算对照**：任何一项不同，结论只能写成"两种配置之间的差异"，不能写成"某个组件的贡献"。
- **文案中性（2026-10-19 补，跑之前）**：三个条件的 dispatch 文案必须逐字相同，差异只能是**技能库目录的内容**。这意味着 task_8 / task_9 实际用过的**手写 coordinator addendum 必须撤掉**——那些 addendum 里写着「AABB 不是中心、用逐轴分位数」「闭合读数要按预测宽度校验」「下降自限位即放置」等**库内知识**，留着就是把处理组的知识漏进对照组。保留的只有 `dispatch.py` 里的标准程序性 addenda（单卡、禁区、写回要求），因为它们与技能内容无关且在三个条件里一致。代价是 C2 也要重跑一次——设计里本来就是 6 次有界求解，不是 4 次。

## 1. 主张 2：技能库的贡献（定稿 v1）

### 1.1 变量层

技能库作用于**写程序的 agent**，不作用于程序。因此条件切在「agent 会话开始时能读到什么文本」这一层，测量的是**最终程序在 held-out 上的成功率**。测量对象不是"某次调用"，也不是"某条 trace"。

### 1.2 三个条件（可执行定义）

| 条件 | 技能库目录内容 | 预注册假设 |
|:---|:---|:---|
| **C0 空库** | 只保留 `skills/README.md`（说明与晋升流程，不含任何技能内容）；5 个主题文件不存在 | 基线 |
| **C1 感知级** | `localize.md` 全文 + README；其余 4 个主题文件不存在 | 若感知误差是主要瓶颈（task_9 有 4 个版本耗在 10.63 cm 的定位偏差上），C1 应恢复 C2 差距的**大部分** |
| **C2 满库** | 当前完整库（`3e4cbc21430fa353` 之后的最新 hash） | 上限 |

三条都**保留** `SKILL.md`（管线规则）、`worker-prompt`、verifier 闸门——它们属于**流程脚手架**，不属于技能库内容。若把闸门也关掉，就变成"库+流程"的复合变量，无法归因。

**可选第 4 条件（预算允许时）**：**等长安慰剂库**——把 5 个文件替换成**字符数相当但内容无关**的机器人搬运说明。它能区分"信息有用"与"提示变长更好/更差"（长上下文本身会改变行为）。不跑它时，结论必须写成"库的内容 + 篇幅的联合效应"。

### 1.3 N 的语义（决定）

- **一个 entry = 一个带失败签名头的 `##` 小节**（头字段：`failure-signature` / `when-to-apply` / `fix` / `provenance`）。
- 当前库：5 个主题文件、**27 个 `##` 小节 + 2 个 `###` 子节 = 29 个小节**、932 行（不含 README）——其中含约定/工具类非技能节（如 `grasp.md §Key Conventions`、`localize.md §Key Signals`）；补齐失败签名头后预计 **≈22 个 entry**。
- **本项目不追求论文的 N∈{0,25,50,90} 扫描**：那个曲线需要 90 个可数对象，当前凑不出来，硬凑只会造出 70 个凑数条目。改为报告**阶梯的每一级 N**（0 / 1 文件 / 5 文件），并在论文对标处说明"N 的定义不同，不可直接比曲线"。
- 因此本项目的主张 2 证据形态是**三个条件的阶梯 + 每个任务每节的 verdict 矩阵**，不是一条 N-成功率曲线。

### 1.4 任务集（预注册选择规则）

- 从裁剪后的 5 个任务里取 **2 个**：**task_9**（瓶/架，满库 96%，作为"高上限"端）+ **task_8**（碗/盘，第二个物体族）。
- 选择规则（跑之前写下）：一个任务能进入消融 iff **对比空间存在于 C0 端**——即「一个没有库的 agent 大概率做不出来」。task_9 = 96% 特批入选（C0 端预期低）；task_0 = 0% 不入选（C0 也是 0，无对比空间）。
- **2026-10-19 修正（在看到任何 C0 数据之前）**：原规则写成「C2 ∈ [30%, 95%]」，理由是躲天花板/地板。这个理由不成立——C2 = 100%、C0 = 60% 时差异 40pp 照样可测；真正杀死对比的是 **C0 也接近 100%**。判据因此改成上面那条（看 C0 端），C2 高低本身不作限制。task_8 实测 dev 15/15（预计成为高 C2）仍**保留入选**：它的机制（碗沿翻卷唇的取法、9 mm 伺服滞后、AABB 偏 2.1 cm）正是「没有库就要重新发现」的东西。
- **中止条件**：若 C0 在两个任务上都 ≥ 70%，说明这两个任务对"有没有库"不敏感——**图的对比不成立，报 null 并换任务**，不要靠追加种子救。

### 1.5 seed 分区（决定：不拆）

- 调参只用 **dev 51–65**；**unseen-check 66–80 不进消融**（它的语义是"移交前只测一次"，拿它当消融的测量集会破坏这个语义）；最终测量用 **held-out 1–50**。
- **不做 1–25 / 26–50 拆分**：拆分会把样本砍半、把配对分析的好处丢掉。替代方案是 0 节那条纪律——每个条件的程序冻结后再跑 held-out，held-out 结果不回灌任何条件。
- **配对分析**：同一任务、同一 seed（同一初始场景）在两个条件下都跑 → 按 (task, seed) 配对，用 McNemar / 配对 bootstrap，而非两独立比例检验。配对能消掉场景方差，这是本项目能拿到功效的关键。

### 1.6 判据与功效（先算，再跑）

假设：2 任务 × 50 配对 seed = **100 个配对**；C2 成功率 ~60%，C0 ~45%（即真实差 15pp）。

- 不配对、两独立比例、每条件 250 episode：`SE_diff ≈ sqrt(2·0.25/250) ≈ 4.5pp`，但任务内聚类（ICC ρ≈0.05–0.1）把方差放大 1+(50−1)·ρ ≈ 3.5 倍 → 有效 `SE ≈ 8pp`。
- 配对后场景方差被消掉，有效功效回到接近"不聚类"的水平。
- 结论：**100 个配对上，15pp 的差异约 80% 功效；10pp 只有约 55%。**

**因此判据定为：配对差值 ≥ 15pp（单侧，α=0.05）才算"支持"；10pp 只写成方向性证据**，且必须同时报 CI 与每任务的独立结果。不要事后把阈值改到 10pp——这正是预注册要防的事。

### 1.7 成本

| 项 | 数量 | GPU |
|:---|:---|:---|
| agent 求解（3 条件 × 2 任务，每次 ≤3 个程序版本，只跑 dev 15 seed） | 6 次有界会话 | ≈ 2–3 h |
| held-out（3 条件 × 2 任务 × 50 seed × 42.7 s） | 300 episode | ≈ 3.6 h |
| 合计 | | **≈ 6–9 h + 6 次 agent 额度** |

**intent-to-treat**：某条件在某任务上 3 次尝试内没产出可运行程序，该格记 **0/50**，并单独报"是否产出可运行程序"。这是合法读数（主张预测的正是"没有库就做不出来"），不是执行失败。

### 1.8 已知混淆与不能 claim 的

- **不盲**：协调者知道每个程序属于哪个条件。缓解：跑 held-out 前冻结程序并记录 hash，分析脚本预先提交，结果一次成型。
- **篇幅与内容同变**：C0 短、C2 长。没跑等长安慰剂库时，结论是"内容+篇幅"的联合效应。
- **脚手架本身携带了一部分库知识（保守偏差）**：`dispatch.py` 的常驻 worker addenda 里已经写着「descent 自限位即放置 → 见 `transport.md` §Placement Approach」「near-base descent 有两种相反机制」「第一版全过不要停」等**与库条同源的断言**。三个条件逐字相同，所以不构成混淆，但它把 C0 抬高了、把测得的库效应**压低**。因此本实验的数字应读作**下界**，不是库的全部价值。
- **不能 claim 单条技能的贡献**：C1 只能说明"感知类文本"这一组的作用；要拆单条需要 remove-one 变体（每次去掉一节），成本是阶梯的若干倍，本项目不做。
- **不能外推到别的任务族**：2 个任务、1 个 suite、1 个模型。结论是"这个库在这两个任务上值多少"，不是"技能库普遍有效"。

### 1.9 冻结与可审计

1. 三个条件各自对应的库目录 → 记录内容树 + `sha256`，写进结果文档；
2. 每个条件的程序 → 冻结、记 hash、跑 held-out 前不再修改；
3. 分析脚本（配对检验 + CI）→ 与判据一起预注册；
4. 结果目录 → `outputs/runs/<run>/ablation/claim2/{C0,C1,C2}/{task_N}/`。
5. **每个条件一个独立 run root**（`ablation/claim2/<COND>/runroot/`，含 `campaign.json` + `tasks.json`）。原因不是洁癖：主 campaign 的 `libero-pro/…/task_8|task_9/` 里就放着**解法本身**，若某条臂的 worker 用主 run root 工作，它随时可能读到自己要重新发明的东西。三条臂的 addendum 逐字相同（`ablation/addendum_neutral.txt`），并显式禁止读 `outputs/runs/…/libero-pro/`。

## 2. 主张 1：trace 的贡献（2026-10-20 定稿 v1）

**问题**：最终程序在 held-out 上的成功率里，有多少来自"能看到 run 的 trace"？

**两个条件**。变量层是 agent 在一次会话中能看到的**反馈**；其余全部相同——同一个库
（`b6f72c4bc6ab3354`）、同一套 dispatch 文案（除"你会拿回什么"这一段）、同一 seed 集合、
同一版本预算。

| 条件 | agent 拿回什么 |
|:---|:---|
| **T1**（现状） | 完整 run 目录：`trace/calls/*`、`trace/events.jsonl`、`media/keyframes/`、`media/overlays/`、`outcome.json`、`source/program-result.json` |
| **T0** | **两个文件**：`outcome.json` 里只留 `{program_ok, task_success, termination_reason}`，加 agent 自己程序写的 `source/program-result.json`。没有 `trace/`、没有关键帧/overlay/视频，也没有 `steps_executed`、`timing`、`cumulative_reward` |

**决策（owner 2026-10-20 批准，A1-1…A1-5）**

| 编号 | 决策 | 批准状态 |
|:---|:---|:---|
| A1-1 | T0 给 `task_success` + `termination_reason` + `program_ok`，**外加 agent 自己程序的 report/stdout**；不给 reward / `steps_executed` / timing | 已签 2026-10-20 |
| A1-2 | 关键帧、overlay、视频**一起屏蔽**（图像是最强信息通道；只屏蔽 trace 等于"弱化版"而不是对照组） | 已签 2026-10-20 |
| A1-3 | 任务集：**task_9**（trace 关键格，T1 48/50）+ **task_8**（trace 不敏感对照，T1 48/50）；两者都 ≥30% | 已签 2026-10-20 |
| A1-4 | 判据：同一批 held-out 50 配对种子上成功率差 **≥15pp 且 bootstrap CI 下界 > 0**；先做 **T0 × task_9 × 15 dev seed 的 pilot** 估方差 | 已签 2026-10-20 |
| A1-5 | 公平性：**episode 预算固定**——每格 `8 版 × 15 dev = 120 集 + 1 次 50 集 held-out`，两条件逐字相同；不按成功路径给预算 | 已签 2026-10-20 |

**L-1（A1-1 的取舍，必须写进结论）**：T0 保留 agent **自己程序**的输出，所以 T0 不是"没有任何测量"，
而是"没有**免费的**事后测量"——一个会在程序里打印的 agent 可以自己造出 trace 的一部分，代价是版本和
tick。因此本实验测的是"**per-primitive trace 让测量变免费**"这一条，不是"没有信息也能调试"。这也给了
效应一个上限：真实效应不会超过它。

**L-2（A1-2 的取舍）**：图像与 trace 一起屏蔽，所以测到的是**信息通道整体**的效应，不能拆成"trace 的
功劳"与"关键帧的功劳"。要拆需要第三个条件（屏蔽 trace、保留图像），本轮不做。

**L-3（`docs/` 两臂完全相同）**：`docs/api-reference.md` 已经写着几条**本体常量**（伺服 0.0075–0.011
rad/tick、每次 `move_to_pose` 的固定稳定窗口、`solve_ik` ok ≠ 可伺服）。两臂都给同一份 `docs/`，
因为一个真实 agent 本来就会有它，而且两臂不对称会把"文档"变成第二个变量。代价是 T0 的劣势比
"完全没有测量"窄得多——它**失去的是每次 run 的 trace**，这正是主张 1 的字面表述，但引用结论时
必须把这句话一起引用。

**隔离**：T0 与 T1 各自一个 run root（`outputs/ablation/claim1/{T0,T1}/runroot/`），
与主张 2 同理由——主 campaign 的任务目录里放着解法本身。

**Pilot（下一步，先于全量）**：T0 × task_9，3 版 × 15 dev seed。判读规则**先写死**：
- T0 在 dev 上仍 ≥80% → trace 不是瓶颈，主张 1 的对照需要更强的操纵，**不**直接上全量；
- T0 ≤2/15 → trace 承重，按 A1-4 上 2 任务 × 2 条件；
- 中间情形 → 只加一组重复（2 次求解/格）再判。

### 2.1 Pilot 结果（2026-10-20，一节配对结果）

T0 臂跑满 8 版到 **11/15 dev**（落在"中间区间"），随后把两臂的**冻结程序**都放到 held-out 1–50 上：

| 条件 | 程序 | held-out 1–50 | dev |
|:---|:---|:---|:---|
| **T1** | campaign 的 task_9 `fix_code.py`（v02 就收敛） | **48/50 (96%)** | 15/15 |
| **T0** | 本臂 v05 `fix_code.py`（无 trace，8 版用尽） | **34/50 (68%)** | 11/15 |

配对差 **+0.280**，配对 bootstrap 95% CI **[+0.140, +0.420]**，不一致对 **16 : 2**（T1 独有 16、
T0 独有 2、一致失败 0），精确 McNemar **p = 0.0013** → **A1-4 的判据满足**。

**但 pilot 的判读规则说的是"中间 → 补一组重复"，这一条没有作废。** 已经有的一格配对结果只说明
"效应存在且不小"，不说明"这个数字可复现"：每格仍只有一次有界求解（D-4），+28pp 里有多少是求解之间的
方差，pilot 回答不了。所以下一步是**每格补一次独立求解**，同向才做 A1-3 的第二个任务。

三条必须随结论引用的偏差：**T0 臂用的库反而更强**（`b6f72c4b`，含 task_2 今天提升的夹帽条目，
而它正是靠这一条从 v01 转到 v02 的），所以"更强的库 + 没有 trace 仍然少 28pp"；CI 下界
**+0.140 略低于 15pp**（判据要求的是"差值 ≥15pp 且 CI 下界 > 0"，
两条都满足，但引用时要写全区间）；T1 的程序写在**旧库 `8e4dd2c1`** 上，冻结程序的分数不依赖库，
所以配对有效，且该偏差对 T1 不利 → 结论保守。

报告：`outputs/ablation/results/claim1_report.md`；配对数据 `outputs/ablation/results/claim1/claim1.json`；
分析脚本 `outputs/ablation/claim1/analyze_claim1.py`（判据写死在代码里）。

> **下次从这里开始**：重复求解的操作步骤、环境命令、判读规则与"不要做的事"在
> `outputs/ablation/claim1/HANDOFF.md`（本地，`outputs/` 不入库）。

**T0 的轨迹本身就是主张 1 的证据**：T1 在 v02 到 15/15，T0 用满 8 版（含 3 个 0-tick 自造探针）
才到 11/15，最终机制几乎相同——**差的是到达它的成本，不是能力**（L-1）。其中 v07 专改"承载高度"
却 **0 个种子改变**，T0 无法自己判断改动是否生效；这一条是协调者用"两个版本的通过集相等"挡住的。

## 3. 主张 3：agent 数据的贡献（2026-10-21 重构为三层）

**为什么重构。** 原来这里只有一句话——"程序是数据引擎（蒸馏）"——配一个 BC gate。2026-10-19 那个
gate 给出"必要条件为负"，2026-10-21 查出它测错了对象（§3.4）。但**删掉它之后主张就空了**：一句话的
主张没法判定，也没法知道下一步该不该花钱。所以拆成三层，每层有自己的判据，**前一层的结果决定后一层
做不做**。

| 层 | 主张 | 判据 | 状态 | 成本 |
|:---|:---|:---|:---|:---|
| **3a 数据契约** | 每集的程序、per-call trace、关键帧、逐 tick 动作**严格对齐、可复现、可审计** | 对齐关系逐条可查；同一输入重跑一致 | **已成立**（2026-10-19 交付并验证） | 已付 |
| **3b 信息结构** | 数据里可学的内容集中在"**被测量改写的决策**"上，不在动作流上 | 测量条件调用占全部调用的比例（静态分类 + trace 实测验证） | **待测** | 一天，不占卡 |
| **3c 下游效用** | 这些数据能训出**任务成功率更高**的策略/agent | 闭环任务成功率，带对照臂 | **暂缓**，触发条件见 §3.3 | 两三天起 |

### 3.1 3a 数据契约（已成立，可以写进任何结论）

`scripts/export_agent_rollouts.py` 把一轮 validation 的 `results/` 转成训练索引，不复制像素。在
task_9 的 50 个 held-out episode 上实测：

- 50 集（**48 成功**），**27 827 tick**，每集 7 维关节目标 + 夹爪 + `qpos/qvel/eef_pos/eef_quat`；
- 100 个视频**全部**满足 `frames = ticks + 1`（对齐的硬前提，不是假设）；800×512、20 fps、双视角；
- 产物 4.6 MB（只有索引与 `.npz`，帧留在 mp4 里按需解码）。

**这条主张的强度要说清**：它证明"数据是可用的、对齐是对的"，**不证明"数据有价值"**。前者是工程事实，
后者是 3b/3c 的事。

### 3.2 3b 信息结构（下一步就该做的那个）

**主张句**：agent 的调用参数里，有相当比例是**被运行时测量改写**的（闭合宽度、点云分位、短欠量……），
而不是被程序文本预先决定的；**这部分才是"agent 数据"相对"程序文本"的增量信息**，也才是可学的部分。
动作流本身只是这些决策的机械展开。

**为什么不是"能不能预测下一步决策"。** 那个问法有两个坑，而且这个项目都踩过：

1. **它是代理指标。** "决策预测准确率"可以很高而毫无意义——最常见的调用是"往下走 2 cm"，学会输出它
   就能拿到不低的分数。今晚已经有两个代理指标骗过人：`p=0.0013` 的 +28pp 没能复现；逐 tick MAE
   0.0019 rad 是恒等式。
2. **它近乎同义反复。** agent 的决策**本来就是程序文本的函数**。给模型源码，它能预测得几乎完美；这
   不说明数据有价值，只说明程序是确定性的。

真正的问题不是"能不能预测"，而是"**哪一部分决策不是程序文本决定的**"。

**做法**（全部离线，不需要仿真）：

1. 取两轮 campaign 加主张 1 的全部程序版本（task_2/5/8/9，加 task_9 的 8 个消融版，几十个普通
   Python 文件）。
2. 用 `ast` 对每个调用点的每个参数分类来源：**字面常量** / **程序内部计算** / **某次工具调用的输出**。
3. 报三个数：`测量条件参数 / 全部参数`、`测量条件调用 / 全部调用`、以及这些点在**种子间是否真的变化**
   ——用 trace 里记录的实测值验证分类，这一步把"静态猜测"变成"实测"。
4. 附一份清单：这些点是什么（闭合门、接触判据、瞄准来源、回退分支），因为这清单本身就是下一步要
   验证"库里该写什么"的素材。

**判据（先写死）**：

| 测量条件调用占比 | 结论 | 下一步 |
|:---|:---|:---|
| **< 10%** | 主张 3 收敛为 3a；数据价值在**程序与验证**，不在训练策略 | 蒸馏路线改**程序合成（SFT）**，**3c 不做** |
| **≥ 25%** | 3b 成立：数据里有可学的决策结构 | 3c 值得做，按 §3.3 的设计 |
| 10–25% | 只报结构，不下结论 | 需要第二个任务的同类分析再判 |

**成本**：一天，纯 CPU。**风险**：静态分类会有误判，所以第 3 步的 trace 验证是必须的，不是可选的。

### 3.3 3c 下游效用（暂缓，附触发条件）

这是原来那句话（"蒸馏"）真正想说的东西：**用这些数据训出来的策略，任务成功率更高。** 暂缓的理由不是
贵，是**现在做出来不可归因**：

- 单任务训练集只有 **38 集 / 约 2.1 万 tick**（task_9 的 48 个成功 episode 减去 10 个留出）。在这个规模上
  闭环结果的两种可能都不能支持主张：0–5% 成功分不清"数据没用"和"38 集训不出来"；偶尔成功则没有对照
  臂，分不清是数据还是任务简单。
- 要可归因，最自然的对照是**数据量阶梯**（12 / 24 / 48 集各训一个策略，看成功率随 N 上升），而不是
  单次闭环。那是 3 次训练 + 3 次闭环 sweep ≈ **两三天**，仍然只有一个任务。
- 库里的成功 episode 其实不止 task_9 的 48 个：**task_2 50 + task_8 48 + task_9 48 = 146 个**，分布在
  三个任务上。但导出器目前只跑过 task_9；多任务要语言/任务条件化，是另一个量级的工程。

**顺带修正一条旧判断**：本文件重构前的 §3.2 说"闭环评测需要 harness 扩展（policy provider + 新原语）"，这句话
把障碍说大了。沙箱只限制**程序内**不能 `import torch`，不限制我们自己的脚本——写一个独立 driver
（照 `run_validation.py` 建 env，逐 tick `step(policy(obs))`）就够，**不需要动 cap-harness**，一天量级。

**触发条件（写死）**：3b 的测量条件调用占比 **≥ 25%**，且那时能导出 ≥2 个任务的 rollout。两者不同时
满足，3c 不做——**"数据能不能训出策略"就明确记为未测，而不是记为负结果。**

### 3.4 留作反面教材：逐 tick teacher-forced MAE 不能当判据

2026-10-19 的 gate（`scripts/train_bc_gate.py`，38 集训练 / 10 集留出）：

| 臂 | MAE (rad) |
|:---|---:|
| 训练集均值动作 | 0.2525 |
| **复制上一 tick 的动作（lag-1）** | **0.0019** |
| 只给本体感受（MLP） | 0.0663 |
| 图像 + 本体 | 0.0692 |

当时读作"必要条件为负"。2026-10-21 重查（`outputs/ablation/results/claim3_report.md`）：

1. **指令流是分段常数的**：777 个 episode / 31.2 万 tick，**89.4%** 的相邻 tick 目标完全相同，平均一次
   调用覆盖 9.2 个 tick。lag-1 的 0.0019 不是"好模型"，是恒等式。
2. **模型输入里没有 `a_{t-1}`**，而基线拿的正是它。补上之后（`--prev-action`）本体臂 **0.0661 → 0.0315**。
3. 即便公平了，仍差 lag-1 **16 倍**；且 `state` 与 `image+state` 复现时给出**同一个 0.0661**——两个模型
   塌到同一个平凡预测。**换模型解决不了指标问题。**

若将来还是想要一个便宜的离线门禁，三条必须同时满足：每个臂都含 `a_{t-1}`、在**变化 tick** 或**每次
调用**上评分、并同时报同口径下的恒等基线。`scripts/train_bc_gate.py` 为此新增 `--prev-action`（默认
关闭），2026-10-19 的记录仍可用原命令复现。

### D-4 每格只有一次有界求解（最重要的限制）

> 在 task_9 上，**一次**空库求解 0/50，**一次**满库求解 X/50；在 task_8 上两者都是 48/50。

是误用；要得到效应量需要每格多次独立求解，成本约为本实验的 3–5 倍。

### D-5 任务选择本身是一次事后教训

task_8 被选中是因为它是"第二个物体族"，但它恰好是一个**强模型能从文档与几何推出来**的任务，因此对

写成：**优先选"关键知识是本体验证过的经验事实"的任务**，例如需要问"这个姿态族在本体上能不能伺服"的任务。
